# TL;DR Document Extraction (PDF/DOCX) — Design

**Date:** 2026-08-12
**Status:** Implemented

## Goal

Enhance the extension's existing TL;DR feature (`extension/panel.js:1016`) so that when the active tab's document *is* a PDF or a modern Word (`.docx`) file — not an HTML page — TL;DR extracts and summarizes that document's actual text content, instead of the empty/garbage result it would currently get from scraping `document.body.innerText` on a non-HTML tab.

**Scope:** the current tab IS the document (the user navigated directly to a `.pdf`/`.docx` URL — the same way Chrome's built-in PDF viewer already works today). Summarizing a document merely *linked from* an HTML page the user is browsing is out of scope. Legacy binary `.doc` (pre-2007 OLE format) is out of scope — only modern `.docx` (OOXML/ZIP). This only changes the `tldr` button — Translate and the CVE-selection flows are untouched.

## Why this isn't just a file-type check

Today, `readCurrentPage()` (`panel.js:803`) always uses `chrome.scripting.executeScript` to inject a function into the active tab and read `document.body.innerText`. Two things break this for PDFs and DOCX:

1. **Chrome's built-in PDF viewer blocks script injection into it entirely** — already documented in `CLAUDE.md`/`background.js:26-27` as the reason the CVE-selection flow uses the browser-level right-click context menu instead of a content script for PDFs. `chrome.scripting.executeScript` hits the same restriction `readCurrentPage()` would need to work around.
2. **`.docx` isn't rendered by Chrome at all** — there's no DOM to scrape. The tab shows a blank page or Chrome's download UI; `tab.url` is the only usable signal.

Extracting real text therefore requires fetching the document's raw bytes directly (from the side panel's own extension context, not injected into the tab — which also sidesteps restriction #1 above) and parsing the file format client-side.

Two architectures were considered for the *parsing* step:
1. **Hand-roll both PDF and DOCX parsers, zero dependencies** — consistent with this extension's current zero-vendored-library pattern (mirrors `serve.py`'s stdlib-only rule), but PDF text extraction done naively (parsing `Tj`/`TJ` content-stream operators) is high-risk: it will likely produce garbled or missing text on any PDF using embedded/subset fonts with custom encoding — extremely common for anything generated by Word, LibreOffice, or report tools, including this project's own compliance-PDF exports. A security engineer summarizing a compliance or vendor report could get a confidently-wrong summary with no signal that extraction failed.
2. **Vendor pdf.js for PDF, hand-roll DOCX.** pdf.js (Mozilla's library — the same engine Chrome's own built-in PDF viewer uses) handles the hard cases naive parsing doesn't: embedded fonts, compressed streams, multi-column layout. DOCX stays dependency-free since it's genuinely simple (a ZIP of XML, no font/encoding complexity). **Chosen.** This is the first third-party dependency added to this extension; the trade-off (reliability of real-world PDF text, for a project that already generates and expects to summarize security/compliance PDFs) favors correctness over dependency purity here.

## Design

### 1. Detection & flow

`readCurrentPage()` branches three ways instead of assuming HTML:

1. Get `tab.url` via `chrome.tabs.query({ active: true, currentWindow: true })` (already how the extension gets the active tab today — no injection needed for this step).
2. `fetch(tab.url, { credentials: 'include' })` directly from the side panel's own context. `credentials: 'include'` is used so an already-logged-in session's cookies are sent for internal/auth-walled documents (e.g. an internal SharePoint/Drive-hosted report) — if the user isn't logged in, the server may return an HTML login page instead; see Error Handling.
3. Branch on the fetched bytes' **magic number**, not the `Content-Type` header: read the first 4 bytes of the response `ArrayBuffer` and check for `%PDF` (PDF) or `PK\x03\x04` (ZIP — the container format `.docx` uses). `Content-Type` is not used for detection — many servers serving downloadable files send generic `application/octet-stream` instead of the correct type, which would silently misdetect a real PDF/DOCX and send it down the broken HTML-scrape path. Magic-byte sniffing is cheap (a handful of bytes) and doesn't depend on the server getting headers right:
   - `%PDF` → PDF extraction (§2)
   - `PK\x03\x04` → attempt DOCX extraction (§3) — if it turns out to be a ZIP that isn't actually a `.docx` (no `word/document.xml` inside), §3's existing "Couldn't read this as a Word document" error handles that; no separate detection step needed for "is this really a docx" beyond just trying to parse it as one
   - anything else → fall back to the existing `chrome.scripting.executeScript` DOM-scrape, **completely unchanged** from today's behavior

Extension pages (like the side panel) fetching a URL covered by `host_permissions` (already `https://*/*` in `manifest.json`) aren't subject to the target server's CORS policy the way a normal webpage's `fetch()` would be, so this works for arbitrary external document URLs, not just same-origin ones. No `connect-src` CSP change is needed — `https:` is already wildcarded there.

### 2. PDF extraction (pdf.js)

**Correction from initial approval:** pdf.js dropped its global-script (UMD) build entirely as of v4.0 — current releases (confirmed against 6.2.108, the latest at design time) ship only ES modules (`.mjs`), in both the `build/` and `legacy/build/` trees of the `pdfjs-dist` npm package. There is no non-module distribution anymore. This doesn't change any decision already approved (still vendoring pdf.js, still client-side) — it changes how it's loaded.

Vendor pdf.js's `build/` tree (not `legacy/build/` — that name no longer means "non-module," only "transpiled for older browsers," and this extension only targets Chrome) under `extension/vendor/pdfjs/`: `pdf.min.mjs` + `pdf.worker.min.mjs` (~1.7 MB combined, minified). Loaded from `panel.js` (which stays a classic script — no `type="module"` conversion needed) via dynamic `import()`, which works from a classic script context in MV3 extension pages:

```js
const pdfjsLib = await import(chrome.runtime.getURL('vendor/pdfjs/pdf.min.mjs'));
pdfjsLib.GlobalWorkerOptions.workerSrc = chrome.runtime.getURL('vendor/pdfjs/pdf.worker.min.mjs');
```

Flow: `pdfjsLib.getDocument({ data: arrayBuffer }).promise` → for each page, `page.getTextContent()` → join text items with spaces/newlines in reading order → truncate to `PAGE_MAX_CHARS` (the same 12000-char constant TL;DR already uses for HTML pages — no new truncation logic, same downstream summarization prompt).

**CSP:** no `unsafe-eval` needed. Text extraction (`getDocument`/`getTextContent`) never touches the PostScript-function-compilation path (used only for shading/rendering, which this feature never does), and that path compiles via WebAssembly rather than plain `eval` anyway. To be precise about MV3 here (an earlier draft of this section overstated it): `wasm-unsafe-eval` is a source expression MV3 *permits* an extension to add to its own `script-src` — it is not granted by any baseline/non-relaxable default. This extension declares `script-src 'self'` with no `wasm-unsafe-eval`, so WebAssembly is currently blocked in its extension pages. That's fine for this feature: in the vendored build, WASM is only used for image decoding (JPX/QCMS), which text extraction never reaches. No CSP change needed here beyond what §5 covers for the worker file itself.

Two PDF-specific error cases (see also §4):
- **No text layer** (scanned/image-only PDF): every page's `getTextContent()` returns empty items. Detected explicitly and surfaced as a clear message rather than silently summarizing nothing.
- **Encrypted/password-protected PDF**: pdf.js throws an error with `name === 'PasswordException'` (stable across versions, confirmed unchanged in 6.2.108) — caught and surfaced as a clear, specific message rather than a generic parse error.

### 3. DOCX extraction (hand-rolled, no dependency)

A `.docx` is a ZIP archive of XML parts. No library needed:

1. Parse the ZIP local file headers by hand (well-documented binary format: signature, filename, compression method, compressed size) to locate the `word/document.xml` entry.
2. Decompress it with the browser's native `DecompressionStream('deflate-raw')` — available in Chrome for years, no library needed.
3. Parse the resulting XML with `DOMParser` and walk `<w:p>` paragraphs in document order, concatenating each paragraph's `<w:t>` runs (OOXML splits runs mid-word on formatting/rsid boundaries, so runs are joined with nothing between them) and joining paragraphs with `\n\n` — the same separator the HTML scrape path produces.
4. Truncate to `PAGE_MAX_CHARS`, same as everything else.

Error case: if `word/document.xml` isn't found in the ZIP (corrupt file, or a legacy `.doc` mislabeled `.docx`), surface "Couldn't read this as a Word document" rather than a cryptic exception.

### 4. Error handling

The existing `withPage()` wrapper (`panel.js:839`) already catches any exception from its callback and shows `"Could not read page: {message}"` — this stays the outer safety net for everything below. Each extraction path throws with a specific, human-readable message so that catch-all is useful rather than a raw stack trace:

- Fetch fails (network error, non-2xx status) → "Could not fetch document: {status/message}"
- PDF, no text layer → "This PDF appears to be scanned/image-based with no extractable text — OCR isn't supported."
- PDF, password-protected → "This PDF is password-protected."
- DOCX, `word/document.xml` missing/corrupt → "Couldn't read this as a Word document."

**Known, accepted limitation (not solved in this design):** if a document requires login and the current session isn't authenticated, the server may return an HTML login page instead of the file. The magic-number check would see neither `%PDF` nor `PK\x03\x04` and fall through to the regular HTML-scrape path, so TL;DR would summarize the login page's text — confusing, but not a crash. Reliably detecting "this is actually a login page" is unreliable heuristic territory and isn't worth building for v1.

### 5. Manifest/CSP changes

- `web_accessible_resources`: add an entry for `vendor/pdfjs/*` (covers both `pdf.min.mjs` and `pdf.worker.min.mjs`). pdf.js instantiates its worker internally as `new Worker(workerSrc, { type: "module" })` once given a resolvable URL via `GlobalWorkerOptions.workerSrc` — MV3 practice is that this needs `web_accessible_resources` even when the loading page is the extension's own, since worker instantiation is treated as a fetchable-resource access, not an internal script `import`. The implementer should still verify this in practice (load the extension, confirm no "resource not web accessible" console error) rather than trust this note alone.
- CSP: **no changes needed.** No `unsafe-eval` (see §2 — text extraction never needs it; nor is `wasm-unsafe-eval` needed, since the WebAssembly path pdf.js uses elsewhere is image decoding, which this feature never reaches). No `worker-src` addition needed — it isn't currently set, so it inherits from `script-src 'self'`, and the worker file lives under the same extension origin.
- No `connect-src` change needed (see §1).

## Out of scope

- Summarizing a document merely linked from an HTML page (only the current tab's own document, per Scope above).
- Legacy binary `.doc` (OLE format) — only modern `.docx`.
- OCR for scanned/image-only PDFs.
- The Translate button and CVE-selection flows — unchanged.
- Detecting/handling login-walled documents beyond sending existing session cookies (see §4's known limitation).
- `chatbox.html` (standalone, non-extension UI) — not part of the original ask, consistent with how other recent extension-only features have scoped it.

## Testing plan

No automated test suite exists in this repo (per `CLAUDE.md`). Verification is manual:

1. Open a real text-based PDF directly (e.g. a public spec/report PDF) → TL;DR summarizes it correctly.
2. Open a real `.docx` URL directly → TL;DR summarizes it correctly.
3. Open a scanned/image-only PDF → clear "no extractable text" message, not a garbled or empty summary.
4. Open a password-protected PDF → clear "password-protected" message.
5. Open a `.docx`-named URL that's actually something else (corrupt/mislabeled) → clear error, not a crash.
6. Open a regular HTML page and confirm TL;DR behaves exactly as it does today (regression check — the most important one, since it's the existing, working path).
7. Check the DevTools console for CSP violations when the pdf.js bundle loads.
